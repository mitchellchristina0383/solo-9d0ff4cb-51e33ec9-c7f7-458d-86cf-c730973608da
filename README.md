# 流式故障切换网关（FastAPI + 两个可复现本地模拟节点）

在网页输入提示词与输出词元上限，观察回复**逐词元生成**；首节点（node-a）中途
超时后，网关用「原提示词 + 已采纳词元」让备用节点（node-b）续写。网关只追加
新词元、忽略首节点迟到回包，整条回复共用一个词元上限；接续成功时结果与无故障
场景**逐词元完全一致**；两节点模型/分词器版本不一致或备用续写失败时，保留已
显示文本并标记为**未完成**。

新增：**公共上下文预热 / 前缀缓存**。推理页把「公共上下文」与「本次问题」分开
输入，一键把同一段上下文提前送到 node-a / node-b 两台节点预热；每台节点只保留
**最近一次成功预热**的计算结果（新预热替换旧的，重启即丢失）。生成与主备接续
都以提交时的完整输入（`上下文 + 问题`）为准：命中就复用已做的上下文计算，缓存
被替换或因重启丢失就按原文重算；命中与否产出的词元序列**逐位一致**（并发提问、
中途换上下文预热同样成立）。网页按实际参与生成的节点显示命中/重算情况。

## 架构

```
浏览器 (web/)  ──SSE──▶  网关 gateway/app.py  ──SSE──▶  node-a (首节点)
                          │  读超时/出错后                │  挂起后仍产生
                          └──────────────▶  node-b (备用)  └─▶ 迟到回包（被忽略）
       POST /api/preheat ─▶ 网关并发扇出 ──▶ 两台节点各自预热公共上下文（单槽缓存）
```

* `common/deterministic.py`：确定性「解码」。第 i 个词元是
  `sha256("mock-llm/v1:" + prompt + ":" + i)` 对共享词表取模的纯函数，无随机数、
  无时钟、无机器标识。两个节点共用同一模块，因此健康续写必然复现同一词元流，
  结果可复现（同提示词多次请求、跨节点结果一致，有测试覆盖）。另有
  `context_state(context)`：模拟对公共上下文做 prefill/KV 计算的纯函数（摘要），
  作为「上下文计算结果」的替身——重算必然得到同一状态，因此缓存只决定
  「复用还是重算」，绝不影响词元输出。
* `node/app.py`：同一个 FastAPI 应用部署为 node-a / node-b 两个实例，SSE 流式
  输出 `meta / token / error / done` 事件；支持按请求注入挂起、失败、版本伪装，
  并在挂起后由脱离请求的后台任务继续产生「迟到回包」（记录在 `/debug/late`）。
  新增 `POST /preheat`（单槽缓存，只留最近一次成功预热）、`GET /cache`（槽位
  状态与预热/命中/重算计数）；`/generate` 请求体新增 `context` 字段，流内
  `meta` 事件携带 `cache_hit` 与 `context_state`。
* `gateway/app.py`：编排状态机，负责读超时判定、只追加接受、共享预算、身份校验
  与故障切换，并向浏览器转发 SSE 事件。新增 `POST /api/preheat`（把同一段上下文
  并发扇出到两台节点）、`GET /api/cache`（聚合两节点缓存状态）；`/api/chat`
  新增 `context` 字段，完整输入 = `context + prompt`，主备两路共用。
* `web/`：原生 HTML/CSS/JS 单页，逐词元渲染（按来源节点着色）、展示切换/未完成
  事件，并自动与 `/api/expected` 的无故障基准核对。新增公共上下文输入框、预热
  按钮、两节点缓存状态栏，以及按实际参与生成的节点显示的命中/重算标记。

## 启动

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://localhost:8080
```

三个服务：node-a、node-b（仅内网 expose，带健康检查）、gateway（映射 8080）。
节点每 0.12s 出一个词元，网关读超时 `GATEWAY_READ_TIMEOUT=1.0s`，挂起场景会在
约 1s 后触发切换。

### 无 Docker 时本地运行（本机试跑所用方式）

```bash
python -m pip install -r requirements.txt
python run_demo.py          # 真实 uvicorn + HTTP 跑全部场景与预热演示并打印核对报告
python -m pytest            # 18 项端到端/单元行为测试
```

## 公共上下文预热 / 前缀缓存

* **分开输入**：网页提供「公共上下文」与「本次问题」两个输入框；网关把完整输入
  定义为 `context + prompt`（直接拼接，上下文里可自带换行/标点），主节点请求与
  备用节点续写请求都携带同一份完整输入与 `context` 字段。
* **预热**：`POST /api/preheat {"context": "..."}` 由网关并发扇出到 node-a 与
  node-b 的 `POST /preheat`。节点把 `context_state(context)`（模拟 KV/prefill
  计算）存入**单槽缓存**：只保留最近一次成功预热，新预热替换旧条目（响应带
  `replaced`/`refreshed` 标记），缓存只在进程内存中，重启即空。
* **命中判定**：`/generate` 在提交时完整输入到达后查一次缓存——`context` 非空、
  与槽中条目完全一致、且确实是本次 prompt 的前缀，三者同时满足才算命中，复用
  已算状态；否则（未预热、被新预热替换、重启丢失、上下文并非前缀）按原文重算
  `context_state`，重算结果**不写回**缓存（只有 `/preheat` 会填充）。
* **一致性**：词元是完整输入的纯函数，与缓存无关；命中/未命中、并发提问、生成
  途中换掉预热上下文，回复都与直接计算逐词元一致（有专门测试）。
* **命中展示**：节点在流内 `meta` 里上报 `cache_hit`，网关为每个**实际参与生成**
  的节点向浏览器转发一个 `cache` 事件，并在 `done`/`incomplete` 里带
  `cache: {节点: 是否命中}` 汇总；网页据此渲染命中/重算标记，另有常驻的
  两节点缓存状态栏（`GET /api/cache`）。

手动验收流程（Docker Compose）：`docker compose up --build` 后开两个网页标签
——标签 1 填公共上下文点「预热上下文到两台节点」；标签 2 用同一上下文提问
（healthy），应显示 node-a 命中；标签 1 换 `failover_success` 场景再生成，应看到
node-a、node-b 先后命中且词元与基准一致；标签 2 换一段上下文再预热，标签 1 用
原上下文生成，应显示未命中重算、词元仍逐位一致。

## 四个演示场景（网关侧按请求注入，可重复）

| 场景 | node-a 行为 | node-b 行为 | 最终结果 |
|---|---|---|---|
| `healthy` | 正常生成 | 不参与 | 12/12 词元，基准结果 |
| `failover_success` | 第 4 个词元后挂起 → 网关读超时 | 用原提示词 + 4 个已采纳词元续写 | 12/12，与 healthy **完全一致** |
| `failover_backup_error` | 同上挂起 | 续写至绝对下标 7 时失败 | 保留 7 个词元，标记未完成 |
| `version_mismatch` | 同上挂起 | 伪装为 `mock-llm-7b-hotfix` / `tok-v2` | 拒绝接续，保留 4 个词元，标记未完成 |

## 需求与实现的对应

1. **网页输入提示词与词元上限、逐步生成**：`web/index.html` + SSE，每个 `token`
   事件即时追加渲染，计数器实时更新。
2. **首节点中途超时与迟到回包**：节点收到 `stall_before` 后挂起；网关用
   `asyncio.wait_for` 做**逐事件读超时**（不是整体请求超时）。挂起节点脱离请求
   的后台任务 1.5s 后继续产出迟到词元并打日志/落 `/debug/late`。
3. **备用节点用原提示词 + 已采纳词元续写**：网关携带 `prompt`、`start=已采纳数`、
   `accepted_ids`、剩余预算调用 node-b；节点侧对 `accepted_ids` 做前缀校验
   （不匹配返回 409）。
4. **只追加、忽略迟到输出、单一词元上限**：网关维护 `next_index`，只接受严格
   等于下一下标的词元，重复/乱序（含迟到）一律忽略；备用节点预算为
   `max_tokens - 已采纳数`，全流总量恒等于一个上限。前端有同款下标守卫。
5. **接续成功与无故障一致**：确定性解码 + 绝对下标续写，测试与页面对照
   `/api/expected` 双重断言词元 id 序列逐位相同。
6. **版本不一致 / 续写失败 → 保留已显示文本并标未完成**：切换前网关先 GET
   node-b `/info` 比对 `(model_id, tokenizer_version)`，不一致直接发 `incomplete`
   且不发起续写；续写流返回错误或提前结束同样发 `incomplete`，事件中带回完整
   `prefix_text`，已下发词元不会被撤回或改写。

## SSE 事件（网关 → 浏览器）

`meta`（请求信息，含上下文长度）→ 可选 `cache`（每个实际参与生成的节点一条：
命中或按原文重算）→ 若干 `token`（含绝对下标 index、词元 id、来源 node）→
可能的 `fallback`（切换原因与已采纳数）→ 备用节点的 `cache` → 更多 `token` →
`done`（完成，含各节点词元占比与各节点命中汇总）或 `incomplete`（原因、身份
信息、保留前缀、命中汇总）。

本机（无 Docker，使用真实 uvicorn socket）已跑通：

* `python -m pytest`：**18/18 通过**。原 8 项（健康基准、接续等价性、共享预算、
  备用失败、版本不一致、迟到回包被忽略、节点前缀校验、跨节点/跨次确定性）+
  新 10 项：预热扇出两台节点、单槽只留最近一次预热（含同上下文刷新）、命中复用
  且与直接计算逐词元一致、被替换后未命中重算仍逐词元一致、生成未命中不写缓存、
  切换场景下两节点都命中且续写一致、替换后切换两节点都重算仍一致、并发交错
  （两路生成 + 中途换上下文预热）逐词元一致、重启后缓存丢失按原文重算、上下文
  非前缀时绝不命中。
* `python run_demo.py`：四个故障场景全部通过自动核对；预热演示六步全过——
  双节点预热、命中生成、切换场景双节点命中且 12/12 词元与基准一致、换上下文
  预热后未命中重算词元仍一致、并发交错三路回复均与各自基准一致、网关聚合缓存
  状态（预热/命中/重算计数）符合预期。
* 静态资源冒烟：`/`、`/app.js`、`/styles.css` 与各 API 均 200；`web/app.js`
  通过 `node --check` 语法检查。

## 遗留事项与简化

1. **Docker Compose 文件未在本机构建验证**：当前环境没有 docker 守护进程；
   compose/Dockerfile 仅做了 YAML 与结构校验（本次功能未新增依赖、未改目录
   结构，镜像无需变化），首次 `docker compose up --build` 建议在有 Docker 的
   环境确认一次（镜像基于 `python:3.11-slim`，结构与本地 uvicorn 启动方式一致）。
2. **「上下文计算」是确定性摘要替身**：`context_state` 只是模拟 prefill/KV 的
   纯函数，用来演示「复用 vs 重算」的契约与命中展示，不代表真实 KV cache 的
   性能收益；真实系统中命中应带来时延/成本下降，这里不做模拟。
3. **缓存不持久化、不跨请求学习**：单槽、每节点独立、重启即失；生成时的重算
   结果按需求不写回缓存（只有显式预热才填充）；无 LRU/容量管理与多槽位。
4. 故障注入是**演示机制**：场景表和 `X-Mock-*` 头只用于可重复演示，生产网关
   不会信任节点的自我身份声明；真实系统应改用带外配置/证书校验模型身份。
5. 仅模拟单一首要→单一备用、一次切换；未实现多级备用、重试退避、熔断与
   跨请求持久化（迟到回包记录保存在节点内存中，重启即失）。
6. 确定性「模型」用词表哈希代替真实推理，重点是可复现的词元契约与切换语义，
   不代表真实 LLM 的解码质量。
7. 前端为零依赖原生页面，未做无障碍/国际化等增强；接口仅做了基本入参校验
   （提示词长度、词元上限 1–128、上下文长度 ≤2000）。
